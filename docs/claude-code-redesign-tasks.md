# 0. Общая инструкция для Claude Code

Перед любым заданием выполнить следующие правила.


## Обязательное использование визуального эталона

Перед каждым этапом открой `docs/redesign-reference/index.html`, затем нужный экран в `docs/redesign-reference/`, если доступен Playwright/browser. Прочитай `docs/redesign-visual-implementation-guide.md` и `docs/redesign-validation-guide.md`. Используй HTML только как визуальный ориентир: не копируй его в `src/`, не переноси демонстрационные KPI/записи/имена/даты в продукт и не имитируй отсутствующие функции. Сверяй результат на 1440, 1024, 768 и 390 px по иерархии, плотности, типографике, статусам, сетке, клавиатурной доступности и мобильной перестройке. После каждого этапа сохрани контрольные скриншоты и перечисли отклонения от эталона.

## Обязательное чтение

1. `AGENTS.md` — прочитать целиком.
2. `README.md`.
3. `docs/redesign-plan.md`.
4. `docs/ui-audit-2026-11-16.md`.
5. `docs/gitgraph-plan.md`, если файл существует.
6. `package.json`, `tsconfig.json`, `playwright.config.ts`.
7. Фактическое дерево `src/`, `tests/`, `e2e/`, `scripts/`, `demo/`.

## Архитектурные ограничения

- Не менять предметную модель и бизнес-правила ради дизайна.
- Не менять 7 ролей, 30 узлов, 37 ситуаций, переходы, права и SLA без отдельного запроса.
- Не переносить проект на React/Vue/Next.js и не вводить другой bundler.
- Не добавлять новые runtime-зависимости без письменного обоснования.
- Сохранять Bun + TypeScript + текущий способ сборки.
- Считать `src/` источником исходников; `demo/app.js` и `demo/style.css` — результат сборки, если актуальный build script подтверждает это.
- Не дублировать правила вычисления SLA, переходов или прав в UI.
- Не придумывать несуществующие данные: ФИО, адреса, телефоны, реальные исполнители, финансы, отправку сообщений и т.п.
- Демо-данные всегда должны быть визуально обозначены как демонстрационные.
- Не имитировать неподдерживаемые операции. Чат остаётся read-only.
- Сохранять старые маршруты `#timeline`, `#chat/...`, `#model` и параметры `at`, `view`.
- Не удалять, не переименовывать и не массово форматировать несвязанные файлы.
- Не делать `git push`, не менять branch protection/Pages/Actions и не коммитить без отдельного поручения.
- Новые TypeScript-модули по возможности держать компактными (ориентир — до 200 строк); разделять обязанности, не дробить без необходимости.
- Следовать действующему `AGENTS.md`, включая правило append-only для его журнала.

## Обязательный цикл работы

1. До изменения описать текущие точки входа и файлы, которые планируется менять.
2. Запустить релевантные проверки до изменений и записать baseline.
3. Реализовать только текущий этап.
4. Добавить/обновить тесты.
5. Запустить проверки после изменений.
6. Собрать demo штатной командой.
7. Просмотреть скриншоты/страницы в целевых размерах, если доступен браузер.
8. Выдать отчёт и остановиться.

Если обнаруживается архитектурный конфликт или требование невозможно выполнить без изменения core, остановиться и объяснить конфликт. Не обходить ограничение скрытым дублированием логики.

## Формат итогового отчёта после каждого этапа

```text
Этап:
Статус: PASS / PARTIAL / BLOCKED
Что сделано:

- bun test: PASS/FAIL/NOT RUN
- bun run typecheck: PASS/FAIL/NOT RUN
- bun run build:demo: PASS/FAIL/NOT RUN
- bun run e2e: PASS/FAIL/NOT RUN
- bun run audit: PASS/FAIL/NOT RUN
Скриншоты/размеры:
Отклонения от плана:
Известные проблемы:
Что требуется от пользователя:
```
