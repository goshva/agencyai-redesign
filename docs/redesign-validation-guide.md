## 1. Структура HTML-эталонов и привязка к URL

Откройте `docs/redesign-reference/index.html` — это каталог всех макетов. Каждый экран находится в отдельном HTML-файле; общие стили и небольшой JS расположены в `assets/`.

| Макет | Файл | Статус маршрута | Маршрут приложения / целевой URL |
|---|---|---|---|
| Обзор / Dashboard | `overview.html` | Предлагаемый | `#dashboard` — сейчас не считать существующим |
| Список обращений | `incidents.html` | Предлагаемый | `#incidents` — сейчас не считать существующим |
| Карточка обращения | `incident-detail.html` | Предлагаемый | `#incident/З-015` — сейчас не считать существующим |
| Хронология Git | `timeline-git.html` | Существующий | `#timeline?at=2026-01-02&view=git` |
| Хронология Гант | `timeline-gantt.html` | Существующий | `#timeline?at=2026-01-02&view=gantt` |
| Переписка | `chat.html` | Существующий | `#chat/З-015?at=2026-01-02` |
| Модель процесса | `model.html` | Существующий | `#model` |

### Важное разграничение

В репозитории есть старые статические страницы в корне (`index.html`, `process.html`, `player.html`, `matrix.html`) и отдельное приложение в `demo/`. Это разные контексты. В этой серии HTML-эталонов целевые экраны относятся к редизайну приложения `demo/`. Не заменять корневые страницы и не считать `docs/redesign-reference/*.html` рабочими страницами приложения.

Существующие маршруты подтверждать по `src/web/router.ts` и E2E-тестам, а не только по этой таблице. Новые маршруты `#dashboard`, `#incidents`, `#incident/З-015` предложены как направление. На Этапе 0 Claude Code должен проверить, как корректно расширить текущий router, и записать итоговую схему в `docs/redesign-baseline.md`. При необходимости имена маршрутов согласовать с владельцем до реализации.

## 2. Одинаковая процедура визуальной проверки

Для каждого этапа, на котором изменяется UI, используйте одинаковые размеры окна:

| Viewport | Что проверять |
|---|---|
| 1440 × 1000 | основная desktop-композиция, ширина контента, плотность и свободное пространство |
| 1024 × 900 | узкий desktop/tablet, сжатие боковой панели и таблиц |
| 768 × 1024 | tablet portrait, перестройка сетки и навигации |
| 390 × 844 | мобильный сценарий, перенос блоков, доступность действий пальцем |

### Как сравнивать с HTML

1. Откройте соответствующий референс из `docs/redesign-reference/`.
2. Откройте рабочую страницу AgencyAI на том же viewport и с тем же примером маршрута/даты.
3. Поставьте браузерный zoom 100%, не меняйте масштаб ОС между скриншотами.
4. Сделайте скриншоты эталона и реализации. Наименование файла должно включать этап, экран и ширину.
5. Сравнивайте сначала крупные области: сетка, размеры колонок, положение заголовков, высоту карточек, sidebar и области прокрутки.
6. Затем проверьте типографику, контраст, бейджи, расстояния, выравнивание и состояния hover/focus/disabled.
7. В конце проверьте поведение: клики, фильтры, ссылки, URL, клавиатуру и мобильную перестройку.
8. Запишите каждое заметное отличие в таблицу отклонений. Не пытайтесь компенсировать несовпадение уменьшением шрифта или скрытием нужной информации.

Не требуется добиваться абсолютного pixel-perfect. Приоритет — одинаковая информационная иерархия и предсказуемое поведение. Реальные данные могут иметь длиннее текст и больше строк, чем заполнение эталона; интерфейс обязан корректно выдерживать такие значения.

### Папки скриншотов

Сохранять артефакты раздельно:

```text

docs/screenshots/redesign-stage-1/

```

Примеры имён:

```text

incidents-1440.png

incident-detail-1440.png
incident-detail-390.png

timeline-gantt-1440.png
chat-390.png

```

Не сохранять дубликаты и временные скриншоты в корень репозитория.

## 3. Проверка на Этапе 0 — инвентаризация и baseline

**Референсы:** открыть каталог, но не менять продуктовый UI.

### Порядок проверки

1. Прочитать `AGENTS.md`, `README.md`, план и задания редизайна.
2. Сверить реальную структуру `src/`, `tests/`, `e2e/`, `scripts/`, `demo/`.
3. Найти фактический router и записать точный синтаксис hash routes и query params.
4. Для каждого из четырёх существующих экранов открыть текущий опубликованный/локальный маршрут: Git, Гант, чат и модель.
5. Проверить, что `at` и `view` восстанавливаются из URL и что перезагрузка страницы сохраняет состояние.
6. Запустить исходные проверки проекта до изменений.
7. Зафиксировать скриншоты 1440, 1024, 768 и 390 px для существующих экранов.
8. Составить карту «макет → маршрут → UI entry point → core/data source → тесты».

### Обязательные результаты

- `docs/redesign-baseline.md`.
- Скриншоты исходного состояния, если браузерное окружение доступно.
- Таблица существующих и предлагаемых маршрутов.
- Список фактических источников данных для заявок, узлов, ролей, SLA, событий и сообщений.

### Критерии PASS

- Ни один продуктовый файл не изменён.
- Записаны реальные функции/типы, а не предполагаемые названия.
- Текущие маршруты сверены по коду и тестам.
- Для всех проверочных команд есть результат PASS/FAIL/NOT RUN и причина.
- Данные, которых нет в модели, перечислены отдельно.

## 4. Проверка на Этапе 1 — дизайн-система и App Shell

**Референсы:** открыть каждый из семи макетов. Главный контроль — любой экран с одинаковым Shell; дополнительно сравнить `overview.html` и `model.html`.

### Порядок проверки

1. Убедиться, что дизайн-токены централизованы, а не продублированы в каждом view.
2. Открыть существующие Git, Gantt, chat и model routes.
3. Проверить одинаковую ширину Sidebar, высоту Topbar, внутренние отступы и внешний фон.
4. Проверить active state пункта меню при каждом маршруте.
5. На 1440 px убедиться, что навигация и контент не конкурируют по ширине.
6. На 1024 и 768 px проверить компактную навигацию и отсутствие перекрытия контента.
7. На 390 px проверить мобильную навигацию, отступы от краёв, safe area и отсутствие горизонтального скролла всей страницы.
8. Пройти интерфейс клавишами Tab, Shift+Tab, Enter, Space и Esc.
9. Проверить focus-visible и контраст всех базовых текстов/состояний.
10. Проверить, что цвета ролей не смешаны с цветами SLA.

### Критерии PASS

- Все существующие экраны открываются через прежние адреса.
- Активный пункт навигации соответствует текущему маршруту.
- Нет глобального горизонтального переполнения на четырёх viewport.
- Клавиатурный фокус видим и не попадает в скрытые элементы.
- Общие компоненты не меняют расчёты или правила core-модели.
- Shell одинаков по геометрии на разных экранах.

## 5. Проверка на Этапе 2 — Обзор и список обращений

**Референсы:** `overview.html` и `incidents.html`.

### Обзор — тестовые сценарии

1. Открыть экран обзора при начальном состоянии модели.
2. Сверить каждый KPI с формулой в документации/selector. Если метрику нельзя достоверно вычислить, её не показывать.
3. Проверить карточки «Требуют внимания»: переход в нужную заявку должен сохранять идентификатор.
4. Проверить, что лента активности упорядочена по времени из модели.
5. Проверить отсутствие ложных данных в пустом состоянии.
6. Убедиться, что цвета статуса дублируются текстом/иконкой.

### Список обращений — тестовые сценарии

1. Открыть реестр и записать общее количество строк.
2. Искать по полному и частичному номеру заявки.
3. Искать по фрагменту доступного текста.
4. Применить каждый фильтр отдельно, затем комбинацию фильтров.
5. Убедиться, что сброс фильтров возвращает исходный набор.
6. Проверить пустой результат.
7. Проверить сортировку, если она включена в этап.
8. Открыть строку клавиатурой и мышью; проверить правильный ID в деталях/URL.
9. Проверить длинные названия и отсутствие обрезания номера, статуса или SLA.
10. На 390 px проверить карточный/адаптивный режим. Горизонтальная прокрутка разрешена только внутри таблицы и должна быть визуально очевидна.

### Критерии PASS

- Нет hardcoded KPI или фальшивых обращений в коде продукта.
- Все списки и фильтры основаны на реальных данных/selector.
- Поиск и фильтры корректны по комбинациям.
- Нет потери текущего набора при переходе к деталям и обратно, если это предусмотрено router.
- Таблица/карточный вид доступны на мобильном и с клавиатуры.

## 6. Проверка на Этапе 3 — карточка обращения

**Референс:** `incident-detail.html`.

### Порядок проверки

1. Открыть карточку по ссылке из списка.
2. Скопировать URL, перезагрузить страницу и проверить прямое открытие той же заявки.
3. Подставить другой существующий ID и проверить, что карточка показывает соответствующие данные.
4. Подставить неизвестный ID: показать понятное состояние «обращение не найдено», не падать и не показывать данные другой заявки.
5. Сверить приоритет, состояние SLA, текущий узел, ситуацию и историю с core-моделью.
6. Проверить паузу SLA: отображение должно отражать core result, не рассчитываться независимо в UI.
7. Проверить, что отсутствующие поля показываются как «не указано»/не отображаются, а не превращаются в 0 или ложный статус.
8. Проверить хронологический порядок событий.
9. Проверить связи с Git/Gantt и чатом: заявка и дата должны передаваться корректно.
10. На 390 px проверить порядок блоков и читаемость карточки.
11. Проверить Esc, фокус и возврат фокуса, если карточка открывается в drawer/modal.

### Критерии PASS

- Deep link ведёт на правильный ID.
- История, статус и SLA совпадают с core.
- Нет самостоятельных UI-расчётов SLA.
- Для неизвестного ID есть корректный empty/error state.
- Не появляются кнопки, имитирующие операции, которых нет в продукте.

## 7. Проверка на Этапе 4 — Git-граф, Гант, чат и модель процесса

**Референсы:** `timeline-git.html`, `timeline-gantt.html`, `chat.html`, `model.html`.

### Git-граф

1. Открыть маршрут с `view=git` и известным `at`.
2. Проверить, что граф показывает только события на выбранный временной срез.
3. Переместить время назад и вперёд; будущее не должно оставаться видимым.
4. Проверить маркеры развилок/слияний и легенду.
5. Открыть событие мышью и клавиатурой; проверить содержимое карточки узла.
6. Проверить внутреннюю горизонтальную прокрутку и подсказку на 390 px.

### Диаграмма Ганта

1. Открыть `view=gantt` с теми же `at` и состоянием данных.
2. Убедиться, что количество и порядок заявок совпадает с Git-графом.
3. Сверить фазу SLA каждой полосы с core selector и Git view.
4. Проверить шкалу времени, подписи и внутреннюю прокрутку.
5. Переключить Git → Gantt → Git и убедиться, что дата/временной срез сохраняются.

### Переписка

1. Открыть `#chat/З-015?at=...` напрямую.
2. Проверить последовательность сообщений и системных событий.
3. Перемотать реплики назад/вперёд.
4. Сменить роль (если действие поддержано текущей моделью) и сверить видимые сообщения.
5. Проверить, что временной срез скрывает будущие сообщения.
6. Проверить 390 px, длинные сообщения и переносы.
7. Убедиться, что интерфейс не обещает реальную отправку: нет активного поля ввода/отправки без backend.

### Модель

1. Проверить число ролей, узлов и ситуаций по источнику данных.
2. Сверить подписи ключевых узлов по `src/data`.
3. Сверить разрешения матрицы по core permissions, не по HTML-эталону.
4. Проверить легенду ✓ / ! / × / — и текстовые пояснения.
5. Проверить sticky header/first column или внутренний скролл на мобильном.

### Критерии PASS

- Старые маршруты и параметры `at`/`view` не ломаются.
- Git и Гант показывают одно и то же состояние данных.
- Временной срез синхронен между хронологией и чатом.
- Матрица прав отражает источник истины модели.
- Чат остаётся read-only, если отправка не реализована.
- Горизонтальный скролл ограничен областью графа/матрицы, а не всей страницей.

## 8. Проверка на Этапе 5 — интеграция и выпуск

### Полный smoke test

Выполнить последовательно:

1. Открыть обзор.
2. Перейти в список обращений.
3. Найти З-015 и открыть карточку.
4. Перейти из карточки в Git-граф.
5. Переключить Git на Гант.
6. Перейти в переписку З-015.
7. Перемотать дату/реплики.
8. Открыть модель процесса.
9. Вернуться к исходной ссылке и перезагрузить страницу.

### Проверки качества

- Unit tests.
- Typecheck.
- Build demo.
- E2E Playwright.
- Accessibility/axe audit.
- Проверка опубликованной GitHub Pages версии.
- Проверка console errors и failed network requests.

Точные команды брать из актуального `package.json` и `AGENTS.md`. Не считать команду успешно выполненной, если она не запускалась; указывать `NOT RUN` с причиной.

### Критерии PASS

- Все обязательные проверки зелёные или baseline-отклонения отдельно объяснены.
- Существующие сценарии и параметры URL работают.
- Новые маршруты не конфликтуют со старыми.
- Нет серьёзных accessibility-проблем.
- Нет глобального горизонтального переполнения.
- Сборка GitHub Pages корректна.
- Финальный отчёт содержит ссылки на скриншоты всех экранов и разрешений.

**Правило:** к следующему этапу переходить только после статуса `PASS` либо после явного решения владельца принять `PARTIAL`. `BLOCKED` означает, что нужно описать конфликт и остановиться, а не обходить его скрытым дублированием логики.
