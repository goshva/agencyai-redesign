## 1. Что находится в каталоге

Каждый экран или view вынесен в отдельный HTML. Каталог открывается локально в браузере без Bun, сервера и внешних библиотек. Общие стили и демонстрационные JS-взаимодействия лежат в `redesign-reference/assets/`.

| Файл | Предназначение | Маршрут |
|---|---|---|
| `overview.html` | Обзор / Dashboard | предлагается `#dashboard` |
| `incidents.html` | Список обращений | предлагается `#incidents` |
| `incident-detail.html` | Карточка обращения | предлагается `#incident/З-015` |
| `timeline-git.html` | Git-граф | существует `#timeline?at=...&view=git` |
| `timeline-gantt.html` | Диаграмма Ганта | существует `#timeline?at=...&view=gantt` |
| `chat.html` | Переписка | существует `#chat/З-015?at=...` |
| `model.html` | Модель процесса | существует `#model` |

Статус маршрута — критически важное различие. Обзор, реестр обращений и детальная карточка являются предложенными новыми экранами. Их route pattern сначала подтвердить по `src/web/router.ts`, затем записать в `docs/redesign-baseline.md`. Существующие маршруты нельзя переименовывать или ломать ради макета.

## 2. Для чего использовать эталоны

HTML-файлы — только визуальные референсы. Они нужны, чтобы Claude Code и разработчик одинаково понимали:

- структуру страницы и приоритет блоков;
- ширину навигации и рабочей зоны;
- размеры карточек, отступы и типографику;
- отображение приоритетов, ролей и SLA;
- адаптацию на desktop, tablet и mobile;
- предполагаемые переходы между экранами.

Не копировать референс целиком в `src/`. Не использовать его как новый runtime. Не переносить демонстрационные KPI, номера, имена, адреса, сообщения, даты, проценты или статусы в приложение.

| Вторичная поверхность | `#F8FAFC` |
| Основной текст | `#172033` |
| Вторичный текст | `#526176` |

## 4. Общая структура приложения

Основная навигация в эталонах: Обзор, Обращения, Хронология, Переписка, Модель процесса. Она задаёт целевую структуру. Для новых пунктов навигации сначала согласовать точные URL с текущим router.

- **Обзор:** краткие показатели, требующие внимания заявки, последние события и общая картина SLA.
- **Обращения:** реестр с поиском, фильтрами, сортировкой и ясным состоянием каждой заявки.
- **Карточка:** сведения о заявке, приоритет, текущий узел, SLA, участники, история и связанные views.
- **Git-граф:** аналитическое отображение прохождения заявок по узлам и ветвлениям.
- **Гант:** альтернативный временной вид тех же данных, не отдельная модель.
- **Переписка:** read-only история сообщений, пока отправка сообщений не поддержана backend.
- **Модель:** справочник узлов и ролей, матрица прав и смысловые обозначения.

## 5. Обязательные адаптивные размеры

Проверять каждый затронутый экран на 1440, 1024, 768 и 390 px. Не ограничиваться уменьшением desktop-макета: мобильная версия должна перестраивать сетки, карточки, панель инструментов и навигацию. Горизонтальный скролл допустим только для широких специализированных областей (Git-граф, Гант, матрица) и должен быть визуально понятен пользователю.

## 6. Источник истины и ограничения

- `src/core` — источник бизнес-правил и вычисляемых состояний.
- `src/data` — источник ролей, узлов, ситуаций, нормативов и демонстрационных сообщений.
- `src/web` — место отображения данных и пользовательского взаимодействия.
- HTML-эталоны — только образец композиции; не источник бизнес-данных.

SLA не пересчитывать в UI. Права не дублировать в presentation-коде. Список заявок, события, история, ветвления, сообщения и доступы должны использовать существующие публичные API модели. Если поле недоступно, скрыть его или показать «Нет данных»; не придумывать содержимое.

## 7. Порядок визуальной приёмки

1. Открыть `redesign-reference/index.html` и выбрать эталон соответствующего этапа.
2. Открыть текущую страницу приложения с эквивалентными параметрами URL и тем же временным срезом, где это применимо.
3. Установить одинаковый viewport и zoom 100%.
4. Сравнить крупную композицию и информационную иерархию.
5. Сравнить плотность, типографику, отступы, бейджи и выравнивание.
6. Проверить все интерактивные состояния и навигацию.
7. Повторить на tablet/mobile.
8. Прогнать автоматические тесты, доступность и сборку.
9. Сохранить скриншоты и записать отклонения.

Детальная инструкция для каждого этапа, список сценариев, критерии PASS и шаблон отчёта находятся в [`redesign-validation-guide.md`](./redesign-validation-guide.md). Не переходить дальше, если текущий этап не получил статус PASS или владелец явно не принял PARTIAL.
