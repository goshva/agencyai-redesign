## 1. Для чего нужен этот документ

Этот документ адаптирует существующий комплект редизайна AgencyAI для работы в **официальном DeepSeek Harness от DeepSeek AI**.

Он не заменяет проектные документы, а определяет, как Harness должен ими пользоваться:

- [`redesign-plan.md`](./redesign-plan.md) — цель, границы и архитектурный план;
- [`redesign-visual-implementation-guide.md`](./redesign-visual-implementation-guide.md) — правила визуального соответствия;
- [`redesign-validation-guide.md`](./redesign-validation-guide.md) — проверка каждого этапа;
- [`claude-code-redesign-tasks.md`](./claude-code-redesign-tasks.md) — подробная последовательность задач и критерии реализации;
- [`redesign-reference/index.html`](./redesign-reference/index.html) — каталог HTML-эталонов.

**Главное правило:** DeepSeek Harness должен выполнять редизайн небольшими проверяемыми этапами, а не пытаться реализовать все экраны за один запрос.

## 2. Что такое DeepSeek Harness в контексте этой задачи

DeepSeek Harness (`dsh`) — агентный рантайм DeepSeek с архитектурой расширений через плагины. Он может предоставлять агенту файловые инструменты, терминал, планирование, поиск, браузерные/компьютерные инструменты, субагентов и другие возможности — состав зависит от выбранного профиля и установленных компонентов.

Для редизайна AgencyAI используйте обычный полноценный профиль/режим работы с репозиторием, в котором доступны как минимум:

1. чтение и поиск файлов;
2. редактирование файлов;
3. запуск команд терминала;
4. просмотр результатов тестов и сборки.

Наличие browser-use, computer-use, subagents, workflow или других дополнительных возможностей **не гарантируется**. Перед использованием агент обязан проверить, какие инструменты доступны в текущем профиле. Если их нет, он должен использовать доступные проверки и явно указать ограничение, а не выдумывать результат.

Официальный репозиторий и документация:

- <https://github.com/deepseek-ai/deepseek-harness>
- <https://deepseek-harness.github.io/deepseek-harness/>
- <https://deepseek-harness.github.io/deepseek-harness/en/guide/providers>
- <https://deepseek-harness.github.io/deepseek-harness/en/reference/tool-catalog>

## 3. Важное предупреждение по безопасности

Официальный проект указывает, что DeepSeek Harness находится в экспериментальной стадии Developer Preview, не прошёл аудит безопасности и не должен считаться безопасным или готовым к production. Он может выполнять сгенерированные моделью команды и код, загружать плагины, обращаться к файлам, процессам, сети и доступным учётным данным.

Поэтому для AgencyAI обязательно:

1. Работать в отдельной локальной копии репозитория или отдельной Git-ветке `redesign/deepseek-harness`.
2. Перед началом проверить `git status` и сохранить/закоммитить пользовательские изменения.
3. Предпочитать режим ограниченной записи в рабочую область и подтверждение опасных действий (например, сочетание уровня `workspace-write` и approval `ask`, если этот preset доступен в установленной версии).
4. Не включать `danger-full-access` и автоматическое одобрение команд для обычной работы над редизайном.
5. Не предоставлять Harness доступ к production-секретам, приватным ключам, паролям, данным пользователей и чужим рабочим каталогам.
6. Не передавать API-ключи в промптах и не записывать их в Git. Использовать штатное хранилище Credentials/Settings Harness.
7. Не устанавливать новые плагины, MCP-серверы и пакеты без отдельного обоснования и подтверждения владельца проекта.
8. Перед запуском потенциально разрушающей команды агент должен объяснить её цель, область воздействия и получить подтверждение.
9. Не запускать непроверенные скрипты из HTML-референсов или сторонних источников в контексте с доступом к реальным секретам.

Рекомендуется иметь резервную копию проекта. Sandbox и approval уменьшают риски, но не гарантируют полной изоляции.

Официальное предупреждение: <https://github.com/deepseek-ai/deepseek-harness/blob/master/SAFETY.md>.

## 4. Подготовка рабочего окружения

### 4.1. Подготовить отдельную копию проекта

Выполняйте команды из PowerShell или терминала, в котором Git и Node.js доступны.

```powershell
# Перейти в папку с рабочими проектами
cd C:\Projects

# Клонировать отдельную рабочую копию, если её ещё нет
git clone https://github.com/BaskakovAnton/agencyai.git agencyai-redesign-dsh
cd agencyai-redesign-dsh

# Проверить состояние репозитория
git status --short
git branch --show-current

# Создать отдельную ветку редизайна
git switch -c redesign/deepseek-harness
```

Если репозиторий уже клонирован, не создавайте второй клон автоматически. Сначала проверьте расположение, ветку и незакоммиченные изменения. Не переключайте ветки и не сбрасывайте файлы, пока не сохранены изменения владельца.

### 4.2. Добавить комплект редизайна

Скопируйте каталог `docs/` из архива редизайна в корень проекта, объединив содержимое с существующим `docs/`. Не удаляйте другие документы проекта.

После копирования должны присутствовать:

```text
agencyai/
└── docs/
    ├── redesign-plan.md
    ├── claude-code-redesign-tasks.md
    ├── redesign-visual-implementation-guide.md
    ├── redesign-validation-guide.md
    ├── deepseek-harness-guide.md
    └── redesign-reference/
        ├── index.html
        ├── overview.html
        ├── incidents.html
        ├── incident-detail.html
        ├── timeline-git.html
        ├── timeline-gantt.html
        ├── chat.html
        ├── model.html
        └── assets/
            ├── reference.css
            └── reference.js
```

### 4.3. Запустить Harness

Официальный краткий запуск Web UI на момент подготовки документа:

```bash
npx @deepseek-ai/dsh web
```

По умолчанию Web UI запускается локально на `http://127.0.0.1:3080`. Актуальную команду и дополнительные параметры проверяйте по официальному README, поскольку CLI находится в Developer Preview.

Запускайте Harness из рабочей папки AgencyAI, чтобы назначить её рабочей директорией текущей сессии. В интерфейсе дополнительно убедитесь, что текущая рабочая область — именно `agencyai-redesign-dsh`, а не другая копия или корень диска.

Официальный источник: <https://github.com/deepseek-ai/deepseek-harness#run>.

### 4.4. Подключить модель

В Web UI откройте **Settings → Models**, выберите DeepSeek или нужного провайдера, настройте API key и модель в соответствии с официальной инструкцией Harness.

Ключи в штатном интерфейсе хранятся в credential storage Harness; не вставляйте их в исходники, проектную документацию, команды shell или сообщения агенту.

Инструкция: <https://deepseek-harness.github.io/deepseek-harness/en/guide/providers>.

### 4.5. Проверить разрешения и инструменты

Перед первым изменением агент должен подтвердить:

- текущую рабочую директорию;
- доступ к чтению и редактированию файлов проекта;
- доступность терминала;
- текущую sandbox/approval-политику;
- наличие средств запуска unit/E2E-тестов;
- наличие браузерной проверки или Playwright, если планируется визуальная автоматизация.

Если нужного инструмента нет — отметить это в отчёте. Не устанавливать плагин только ради обхода отсутствия инструмента без согласования.

## 5. Базовые инструкции агенту

Следующий текст отправляется Harness первым сообщением после того, как рабочая область выбрана.

```text
Ты — ведущий frontend-инженер и технический исполнитель редизайна проекта AgencyAI.

Работаешь в официальном DeepSeek Harness. Твоя задача — реализовать редизайн существующего приложения строго по документации проекта. Не переписывай проект и не меняй бизнес-логику ради внешнего вида.

СНАЧАЛА ПРОЧИТАЙ:
1. AGENTS.md — полностью, если файл существует.
2. README.md и package.json.
3. docs/redesign-plan.md.
4. docs/redesign-visual-implementation-guide.md.
5. docs/redesign-validation-guide.md.
6. docs/deepseek-harness-guide.md.
7. docs/claude-code-redesign-tasks.md — использовать как подробный перечень задач и критериев, несмотря на упоминание Claude Code.

Затем изучи docs/redesign-reference/index.html и все семь связанных HTML-эталонов. Не считай демонстрационные цифры, фамилии, даты, номера и тексты из HTML реальными данными.

ОБЯЗАТЕЛЬНЫЕ ОГРАНИЧЕНИЯ:
- Сохраняй существующий стек и архитектуру. Не внедряй React, Next.js, Vue, Tailwind, новые UI-библиотеки или runtime-зависимости без отдельного обоснования и моего согласования.
- Не переписывай src/core и src/data ради визуальных изменений.
- Не меняй роли, права, узлы, ситуации, переходы, SLA и модель хронологии без отдельного требования.
- Не добавляй backend, базу данных, авторизацию, реальное хранение обращений или отправку сообщений.
- Не выдавай демонстрационные данные за реальные.
- Сохраняй все действующие URL и поведение параметров at/view.
- Изменяй исходники, а не вручную сгенерированные файлы demo/, если AGENTS.md и сборка проекта говорят, что demo генерируется.
- Не редактируй/удаляй чужие незакоммиченные изменения.
- Не выполняй git reset --hard, git clean -fd, массовые удаления, force push, публикацию или изменение секретов.
- Перед потенциально разрушительными командами объясни действие и запроси подтверждение.
- Не устанавливай плагины Harness, MCP, пакеты или новые инструменты без моего разрешения.

ПОРЯДОК РАБОТЫ:
- Выполняй строго один этап за раз: сначала Этап 0, затем жди моей приёмки.
- Не начинай следующий этап, пока я явно не напишу, что предыдущий принят.
- Перед изменениями зафиксируй git status, ветку и baseline.
- Перед каждым изменением прочитай целевые файлы и связанные тесты.
- После изменений запускай только релевантные проверки, найденные в package.json/AGENTS.md; не выдумывай команды.
- Если тест падает до изменений, зафиксируй baseline failure и не приписывай его редизайну.
- При провале проверки остановись, найди причину и исправь; не обходи и не удаляй тест.
- Для каждого затронутого экрана сравнивай реализацию с соответствующим HTML-эталоном на тех же размерах окна.
- Если браузерная проверка недоступна, явно укажи NOT RUN; не объявляй визуальную проверку пройденной.

ФОРМАТ ОТЧЁТА ПОСЛЕ КАЖДОГО ЭТАПА:
1. Статус: PASS / PARTIAL / BLOCKED.
2. Что реализовано.
3. Какие файлы изменены и зачем.
4. Команды, которые были запущены, и точный результат.
5. Какие тесты пройдены / упали / не запускались.
6. Сверка с HTML-эталонами и viewport 1440, 1024, 768, 390 px.
7. Скриншоты и путь к ним, если доступны.
8. Известные отклонения и риски.
9. Что требуется от меня для приёмки.

СЕЙЧАС НЕ ИЗМЕНЯЙ ФАЙЛЫ. Выполни только Этап 0: аудит, инвентаризацию, проверку маршрутов и тестов, фиксацию baseline. Сначала выведи план действий и список инструментов Harness, доступных в этой сессии. Затем выполняй аудит.
```

## 6. Поэтапная работа

Каждый следующий промпт отправляйте отдельным сообщением только после приёмки предыдущего этапа. Текст задач не отменяет проектные ограничения из `redesign-plan.md`.

### Этап 0 — аудит и baseline

**Цель:** понять реальную структуру и поведение проекта до изменений.

Промпт:

```text
Выполни Этап 0 редизайна AgencyAI.

Не меняй продуктовый код и CSS. Проведи инвентаризацию репозитория, прочитай AGENTS.md, README.md и package.json, найди текущие entry points, router, web views, core/data selectors, стили, тесты, E2E, build scripts и механизм генерации demo/.

Подтверди по исходникам и тестам:
- какие маршруты реально существуют;
- как обрабатываются at и view;
- как связаны timeline Git и Gantt;
- где формируются данные заявок, статусы, SLA и сообщения;
- какие функции являются только демонстрационными;
- какие проверки запускаются и какие результаты baseline.

Открой/проверь все семь HTML-эталонов. Составь карту:
экран → реальный маршрут → исходный UI-файл → источник данных → тесты → HTML-эталон.

Создай docs/redesign-baseline.md с фактическими выводами. Если browser screenshot доступен — сохрани исходные скриншоты в docs/screenshots/redesign-baseline/. Если недоступен — укажи NOT RUN и причину.

Не исправляй найденные проблемы в этом этапе. Не придумывай имена функций, маршруты или скрипты. Заверши отчётом PASS/PARTIAL/BLOCKED и жди приёмки.
```

**Приёмка Этапа 0:** baseline содержит подтверждённые файлы, функции, маршруты, тесты и ограничения; продуктовый код не изменён.

### Этап 1 — дизайн-система и App Shell

**Цель:** создать общий визуальный каркас и общие UI-компоненты без изменения бизнес-логики.

Промпт:

```text
Выполни Этап 1 редизайна AgencyAI по docs/redesign-plan.md.

Используй docs/redesign-reference/overview.html и остальные эталоны как источник визуальных пропорций. Используй docs/redesign-visual-implementation-guide.md для цветов, типографики, отступов и состояний.

Реализуй централизованные design tokens, общую оболочку приложения, Sidebar, Topbar, PageHeader, единые базовые состояния интерактивных элементов и адаптивную навигацию. Перед этим используй карту из docs/redesign-baseline.md и работай только с реальными файлами.

Сохрани действующие маршруты и работу URL. Не реализуй пока функциональность новых экранов и не добавляй новые бизнес-сценарии.

Проверь shell на существующих Git, Gantt, chat и model routes. Запусти релевантные тесты. Сверь 1440/1024/768/390 px. Создай отчёт docs/screenshots/redesign-stage-1/ и перечисли отличия от эталона.

Не переходи к Этапу 2. Дай отчёт PASS/PARTIAL/BLOCKED и жди приёмки.
```

**Приёмка Этапа 1:** общая оболочка единообразна, активная навигация корректна, мобильная перестройка работает, старые маршруты не сломаны, тесты пройдены.

### Этап 2 — Обзор и список обращений

**Цель:** реализовать понятную стартовую панель и реестр обращений над существующей моделью.

Промпт:

```text
Выполни Этап 2 редизайна AgencyAI.

Референсы:
- docs/redesign-reference/overview.html
- docs/redesign-reference/incidents.html

Сначала проверь baseline и реальный router. Реализуй экран Обзор и экран списка обращений, расширяя текущую маршрутизацию без изменения старых hash routes. Новые маршруты #dashboard и #incidents используй только если они совместимы с установленным роутером; документируй фактический URL.

KPI, список, статусы, даты, SLA и активность получай из существующей модели и selectors. Не копируй статичные значения из HTML. Если показатель нельзя честно вычислить — не показывай его или явно пометь как недоступный.

Реализуй поиск, фильтры и сортировку только по полям, реально доступным в модели. Сохраняй доступность клавиатуры, пустые состояния и мобильную адаптацию. Если функциональность не обеспечена данными, объясни это и не имитируй её.

Запусти релевантные unit/E2E тесты. Проверь прямую загрузку маршрута, reload, фильтры и переход из строки в карточку/текущий экран деталей. Сравни 1440/1024/768/390 px с обоими эталонами. Скриншоты в docs/screenshots/redesign-stage-2/.

Не переходи к Этапу 3. Отчёт PASS/PARTIAL/BLOCKED и ожидание приёмки.
```

**Приёмка Этапа 2:** данные не захардкожены, поиск и фильтры работают по реальной модели, URL восстанавливается, адаптивность и тесты приемлемы.

### Этап 3 — карточка обращения

**Цель:** дать пользователю понятный экран деталей конкретной заявки/события без изобретения backend-функций.

Промпт:

```text
Выполни Этап 3 редизайна AgencyAI.

Референс: docs/redesign-reference/incident-detail.html.

Сначала определи из core-модели, что именно может быть однозначно представлено как карточка обращения, какие ID и связи доступны, как вычисляются SLA и история событий. Не делай выводы только по демонстрационному ID З-015.

Реализуй экран деталей для существующей сущности/среза модели. Если отдельная заявка как сущность не существует, назови экран и маршрут честно в соответствии с моделью (например, детали обращения в пределах выбранного среза) и зафиксируй это в baseline/плане.

Покажи только реально доступные атрибуты: статус, приоритет, текущий узел/роль, SLA, историю и ссылки на связанные views. SLA не вычисляй повторно в UI. Не добавляй кнопки «назначить», «закрыть», «отправить», если у core нет соответствующих команд.

Обработай неизвестный ID, отсутствующие поля, паузу SLA и длинные тексты. Сохрани переходы в Git/Gantt/chat с верными параметрами at/view.

Запусти релевантные тесты и визуальные проверки на четырёх viewport. Скриншоты в docs/screenshots/redesign-stage-3/.

Не переходи к Этапу 4. Отчёт PASS/PARTIAL/BLOCKED и ожидание приёмки.
```

**Приёмка Этапа 3:** прямое открытие деталей работает, неизвестный ID обрабатывается безопасно, все показатели взяты из модели, нет ложных действий.

### Этап 4 — Git-граф, Гант, переписка и модель

**Цель:** обновить визуализацию сложных процессов, сохранив их семантику.

Промпт:

```text

Используй эталоны:
- docs/redesign-reference/timeline-git.html
- docs/redesign-reference/timeline-gantt.html
- docs/redesign-reference/chat.html
- docs/redesign-reference/model.html

Git view: улучши читаемость узлов, линий, легенды, подписей, масштабирование и переполнение. Сохрани идентификаторы узлов и смысл связей.

Gantt view: улучши шкалу, подписи и различимость фаз. Для одного и того же значения at данные и порядок событий должны соответствовать Git view.

Chat: сделай удобный просмотр сценарной переписки, сохрани роли и системные события. Чётко показывай, что это read-only демонстрация, если отправка сообщений не поддерживается. Не добавляй фальшивое поле ввода.

Обязательно проверь старые URL и параметры at/view. Добавь/обнови тесты на URL-state, переключение Git/Gantt, выбранный узел, chat incident/date и модель ролей.

Сверь каждый экран с отдельным эталоном на 1440/1024/768/390 px. Сохрани скриншоты в docs/screenshots/redesign-stage-4/.

Не переходи к Этапу 5. Отчёт PASS/PARTIAL/BLOCKED и ожидание приёмки.
```

**Приёмка Этапа 4:** Git и Gantt показывают эквивалентный временной срез; семантика и URL сохранены; переписка не имитирует отправку; модель прав не изменена.

## 8. Использование субагентов и параллельной работы

Субагенты, workflow и agent teams можно использовать только при условии, что они действительно доступны в текущем профиле Harness.

Рекомендуемые независимые задачи для возможного делегирования:

- аудит доступности и клавиатурных сценариев;
- проверка соответствия Git/Gantt одному временному срезу;
- review тестов и URL-маршрутов;
- независимая визуальная проверка одного отдельного экрана.

Не делегируйте одновременно нескольким агентам редактирование общих файлов `router`, `app shell`, глобального CSS, токенов или одного и того же view. Сначала назначьте одного основного исполнителя и используйте остальных только для анализа/review. Перед применением изменений из subagent проверьте diff в основном контексте.

Workflow не обязателен для последовательной задачи редизайна. Не создавайте кастомный workflow, plugin или Team-конфигурацию только ради выполнения этих шести этапов.

## 9. Общие правила проверки кода и тестов

1. Перед редактированием прочитать целевой файл и соседние тесты.
2. Сначала выполнять наиболее узкий релевантный тест, затем сборку затронутого слоя.
3. Имена скриптов брать из `package.json`, `AGENTS.md` и текущей документации проекта. Не копировать команды DeepSeek Harness из его репозитория в AgencyAI.
4. Проверки выполняются из корня AgencyAI, не из корня установки Harness.
5. Не изменять тест, чтобы он перестал проверять нарушенную функциональность.
6. Если тест не запускается из-за отсутствующей зависимости или сетевого ограничения, указать точную ошибку и статус NOT RUN/BLOCKED.
7. Сравнивать результаты с baseline, чтобы отделить старые ошибки от регрессий.
8. Не считать успешную сборку доказательством корректности UI.
9. Не считать наличие скриншота доказательством функциональности.
10. Не утверждать, что проверка выполнена, если команда/браузер не запускались.

## 10. Формат отчёта после каждого этапа

Агент обязан использовать следующую структуру:

```markdown
# Отчёт — AgencyAI Redesign / Stage N

**Статус:** PASS | PARTIAL | BLOCKED
**Ветка:** ...
**Commit:** ... (если есть; не создавать без разрешения)

## 1. Результат
- Что готово.
- Что не выполнено.

## 2. Изменённые файлы
| Файл | Изменение | Причина |
|---|---|---|

## 3. Проверки
| Команда / сценарий | Результат | Комментарий |
|---|---|---|

## 4. Визуальная сверка
| Экран | 1440 | 1024 | 768 | 390 | Скриншоты |
|---|---|---|---|---|---|

## 5. Регрессии и риски
- ...

## 6. Отклонения от HTML-эталонов
- ...

- ...
```

Статусы:

- **BLOCKED** — продолжение невозможно из-за ошибки, отсутствия доступа, данных, инструментов или решения владельца.

## 11. Когда агент обязан остановиться и запросить решение

- В репозитории есть незакоммиченные пользовательские изменения, которые затрагиваются редизайном.
- Реальный роутер не поддерживает предложенный URL без изменения контракта.
- В core нет данных, необходимых для обещанного поля или KPI.
- Макет противоречит фактическому смыслу модели, SLA или ролей.
- Для выполнения требуется backend, API, авторизация, хранение данных или отправка сообщений.
- Требуется смена фреймворка, новая runtime-зависимость или переписывание ядра.
- Команда запрашивает доступ вне рабочей директории.
- Требуется включить полный доступ, ослабить sandbox, выключить approval или открыть секреты.
- Предлагается установка плагина, MCP-сервера или дополнительного агента.
- Тесты обнаруживают регрессию, которую нельзя исправить без изменения требований.

При остановке агент описывает факты, варианты решения и последствия; не принимает архитектурное решение за владельца.
