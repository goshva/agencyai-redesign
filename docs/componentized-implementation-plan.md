# Поэтапная реализация и проверка AgencyAI

Работать строго по этапам. Следующий этап начинается только после `PASS` либо явно принятого владельцем `PARTIAL`.

## Этап 0 — аудит и baseline

**Задачи**
- Прочитать `AGENTS.md`, `package.json`, scripts, `src/web/router.ts`, `src/web/*`, `src/core/*`, `tests/`, `e2e/`.
- Зафиксировать существующие маршруты, публичные API модели, состояние тестов и baseline screenshots.
- Установить, какие поля доступны для KPI, SLA, ответственных, сообщений и событий.
- Подтвердить, что новые маршруты `#dashboard`, `#incidents`, `#incident/:id` не конфликтуют с router.

**Проверка**
- Существующие unit/E2E проходят до изменений.
- Записан `docs/redesign-baseline.md`.
- Нет изменений бизнес-логики.

**Gate:** нельзя переходить к реализации, пока не зафиксированы маршруты, API модели и baseline.

## Этап 1 — дизайн-система и общая оболочка

**Задачи**
- Ввести design tokens: цвета, типографика, spacing, радиусы, тени, focus.
- Реализовать Sidebar, Topbar, PageHeader, Panel, Button, Badge, SLA Badge, EmptyState, ReadOnlyNotice.
- Общие состояния: active/hover/focus/disabled/loading/empty/error.
- Адаптивная навигация.

**Проверка**
- Визуально сверить App Shell на всех семи эталонах.
- Viewports: 1440, 1024, 768, 390.
- Клавиатура: Tab/Shift+Tab/Enter/Escape.
- Проверить контраст и доступные имена.
- Не подключать фальшивые кнопки профиля, уведомлений и отправки сообщений.

**Gate:** оболочка не ломает текущие экраны, нет горизонтального overflow на всей странице.

## Этап 2 — обзор и реестр обращений

**Задачи**
- Обзор: KPI, «Требуют внимания», активность, быстрые переходы.
- Реестр: поиск, фильтры, сортировка, пустой результат, переход к карточке.
- Все данные брать из существующей модели/селекторов.
- Для каждой формулы KPI зафиксировать определение и unit test.

**Проверка**
- Сверить `overview.html` и `incidents.html`.
- Проверить поиск по номеру/тексту, сочетание фильтров, сброс, сортировку.
- Проверить пустой результат и отсутствие необязательных полей.
- Сверить counts с источником модели.
- Deep links и Back/Forward.

**Gate:** все KPI и строки объяснимы данными модели; никаких hardcoded demo numbers в runtime.

## Этап 3 — карточка обращения

**Задачи**
- Заголовок обращения, текущий статус, приоритет.
- SLA и основание состояния.
- Данные обращения, текущий узел, участники, история.
- Связи с Git/Гант и перепиской.

**Проверка**
- Сверить `incident-detail.html`.
- Проверить валидный/неизвестный ID, отсутствующие поля, разные SLA-состояния.
- Переходы из списка и обзора.
- URL восстанавливает выбранную заявку и дату.

**Gate:** карточка отражает модель, а не дублирует её правила.

## Этап 4 — Git, Гант, переписка и модель процесса

**Задачи**
- Обновить визуализацию Git-графа и диаграммы Ганта.
- Сохранить маршруты `#timeline?at=...&view=git|gantt`.
- Обновить read-only ChatThread; отправку сообщений не имитировать.
- Упорядочить модель процесса, узлы, связи, роли и права.
- Сохранить `#chat/:id?at=...` и `#model`.

**Проверка**
- Сверить `timeline-git.html`, `timeline-gantt.html`, `chat.html`, `model.html`.
- Дата и выбранная заявка согласованы между views.
- Git/Gantt горизонтальный scroll доступен клавиатурой и имеет accessible name.
- Сообщения только для чтения.
- Значения ролей, узлов, переходов и SLA совпадают с `src/data`/`src/core`.

**Gate:** старые маршруты и сценарии работают без регрессий.

## Этап 5 — регрессия, доступность и выпуск

**Задачи**
- Полный unit, integration и Playwright E2E.
- Responsive: 1440, 1024, 768, 390.
- axe/WCAG 2.2 AA audit, клавиатурный проход.
- Проверка всех deep links, Back/Forward и перезагрузки.
- Сборка demo и проверка GitHub Pages.
- Сохранение before/after screenshots и отчёта.

**Проверка**
- `bun test` (или фактическая команда проекта).
- `bun run build:demo` (если скрипт подтверждён в package.json).
- E2E для обзор → список → карточка → Git/Гант → переписка.
- Нет ошибок console, broken links, overflow и необъяснимых KPI.
- Повторный запуск всех существующих тестов.

**Gate:** релиз только при `PASS` по функциональности, визуальной сверке, адаптивности и доступности.

## Запреты

- Не менять `src/core` ради косметики.
- Не переносить demo numbers, даты, адреса и имена в runtime.
- Не придумывать API, backend или реальные действия.
- Не добавлять UI framework/runtime dependencies без согласования.
- Не редактировать сгенерированные `demo/*` вручную, если они собираются из `src/`.
- Не переходить к следующему этапу при FAIL.
