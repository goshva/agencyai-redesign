## 1. Цель редизайна

Преобразовать текущую техническую демонстрацию модели процессов в понятный, визуально цельный интерфейс системы управления обращениями жителей. Пользователь должен с первого экрана понимать общую ситуацию, быстро находить проблемные обращения и просматривать историю конкретной заявки без необходимости разбираться в Git-графе или внутренней терминологии модели.

Редизайн должен повысить:

- **Наглядность:** статус заявки, ответственный, приоритет и состояние SLA распознаются за несколько секунд.
- **Профессиональность:** единая визуальная система, предсказуемая навигация, аккуратная типографика и согласованные компоненты.
- **Скорость работы:** обзор → список обращений → карточка обращения; основные действия не спрятаны внутри графа.
- **Понимание процессов:** Git-граф, диаграмма Ганта и переписка остаются доступными, но становятся инструментами углублённого анализа.
- **Доступность:** управление клавиатурой, понятный фокус, контраст, семантическая разметка и удобные touch-targets.

Главный принцип: **сначала рабочая информация и следующие действия, затем техническая визуализация процесса.**

## 2. Текущее состояние и ограничения

### 2.1. Что уже есть

Проект использует Bun и TypeScript. Демо собирается в статические файлы для GitHub Pages. Бизнес-модель и UI частично разделены:

- `src/core/` — чистая логика процессов, генерация заявок, граф, навигация, права, SLA, хронология, Git-граф, Гант и переписка.
- `src/data/` — роли, узлы, ситуации, связи, нормативы SLA и демонстрационные тексты сообщений.
- `src/web/` — маршрутизация, представления, HTML/SVG-рендеринг и UI-сессия.
- `demo/` — собранная статическая версия, публикуемая через GitHub Pages.
- `tests/` — unit- и функциональные тесты.
- `e2e/` — Playwright-сценарии.
- `scripts/` — сборка, локальный сервер, скриншоты и аудит UI.

Предметная модель содержит 7 ролей, 30 узлов процесса и 37 ситуаций регламента. Текущая демоверсия включает хронологию с Git-графом, переключение на диаграмму Ганта, карточку узла и сценарный просмотр переписки по ролям.

### 2.2. Ограничения, которые нельзя нарушать

1. Не переписывать `src/core/` ради визуальных изменений.
2. Не менять значения ролей, узлов, ситуаций, переходов, приоритетов и нормативов SLA без отдельного согласования.
3. Не дублировать бизнес-логику в DOM-обработчиках. UI должен вызывать существующие функции модели.
4. Не добавлять backend, базу данных, сетевые API, реальную авторизацию или хранение обращений в рамках этого редизайна.
5. Не создавать впечатление, что демонстрационные данные являются реальными обращениями.
6. Не превращать сценарную переписку в мессенджер: отправка сообщений сейчас не поддерживается. Сохранять заметное указание, что переписка только для чтения.
7. Сохранить существующие URL-маршруты и сценарии:
   - `#timeline?at=YYYY-MM-DD&view=git`
   - `#timeline?at=YYYY-MM-DD&view=gantt`
   - `#chat/<incident-id>?at=YYYY-MM-DD`
   - `#model` (если именно этот hash используется текущим роутером — подтвердить по коду перед изменением).
8. Не редактировать вручную генерируемые `demo/app.js` и `demo/style.css`, если сборочный процесс предполагает их генерацию из `src/`. Источник изменений — исходники, затем `bun run build:demo`.
9. Не добавлять runtime-зависимости и UI-фреймворки без отдельного технического обоснования и согласования.
10. Соблюдать действующий `AGENTS.md`: сначала прочитать его полностью; сохранять стиль архитектуры; не удалять и не переписывать историю проекта; небольшие файлы и функциональный стиль — предпочтительный подход.

### 2.3. Что не входит в этот релиз

- Реальная регистрация/авторизация пользователей.
- Серверное хранение, БД и синхронизация между устройствами.
- Реальное создание, редактирование, назначение и закрытие обращений, если эти команды отсутствуют в модели.
- Отправка сообщений и загрузка вложений.
- Реальные уведомления, email/SMS и интеграции с внешними системами.
- Полноценная производственная отчётность по историческим данным.
- Юридическая проверка регламента и нормативов.

Если для визуального сценария нужна отсутствующая функция, показывать её как демонстрационную/недоступную или не выводить вовсе. Не имитировать успешное выполнение реального действия.

| **Обращения** | Список демонстрационных заявок, поиск, фильтры, сортировка | Новый экран |
| **Хронология** | Git-граф и диаграмма Ганта | Существующий экран, редизайн |

### 3.1. Предлагаемые hash-маршруты

Сначала изучить фактический `src/web/router.ts` и существующие ссылки. Добавлять маршруты без поломки старых:

- `#dashboard` — обзор.
- `#incidents` — список обращений.
- `#incident/<id>?at=YYYY-MM-DD` — карточка обращения/события, если данные модели позволяют однозначно восстановить её.
- `#timeline?at=YYYY-MM-DD&view=git|gantt` — существующая хронология.
- `#chat/<id>?at=YYYY-MM-DD` — существующий сценарный чат.
- `#model` — существующая модель.

Старые ссылки должны продолжать открываться. Не менять формат параметров `at` и `view` без миграционного решения.

## 4. Пользовательские сценарии

### Сценарий A. Руководитель оценивает ситуацию

1. Открывает «Обзор».
2. Видит количество заявок в демонстрационном срезе, просроченные и приостановленные SLA, срочные обращения.
3. Выбирает показатель или блок «Требуют внимания».
4. Переходит к отфильтрованному списку.
5. Открывает нужную карточку.

### Сценарий B. Диспетчер ищет обращение

1. Открывает «Обращения».
2. Ищет по номеру или тексту.
3. Фильтрует по приоритету, состоянию SLA, роли/ответственному или текущему узлу — только если поле существует в модели.
4. Сортирует по срочности/дате.
5. Открывает карточку и проверяет следующий этап.

### Сценарий C. Аналитик разбирает прохождение заявки

1. Открывает обращение или хронологию.
2. Смотрит историю узлов, временные отметки и ветвления.
3. Переключает Git-граф/Гант.
4. Переходит к сценарию переписки на выбранную дату.
5. Меняет дату или роль, не теряя связи с текущей заявкой.

## 5. Визуальное направление

### 5.1. Общая концепция

Стиль: **Enterprise Service Management / Government SaaS**.

Визуальные качества:

- спокойный светлый рабочий фон;
- белые поверхности и хорошо отделённые панели;
- глубокий графитовый текст;
- синий как основной цвет действия и навигации;
- зелёный/янтарный/красный — только для смысловых статусов;
- тонкие границы вместо тяжёлых теней;
- умеренные скругления;
- минимум декоративных градиентов и анимаций;
- понятная плотность данных: удобно на широком экране, без микротекста.

Светлая тема — тема по умолчанию. Тёмную тему сохранять или добавлять только при совместимости с текущим механизмом темы и без дублирования стилей.

### 5.2. Стартовые design tokens

Токены — исходная точка, а не запрет на корректировку после проверки контраста.

| Токен | Значение | Применение |
|---|---|---|
| `--color-bg` | `#F4F6FA` | Фон приложения |
| `--color-surface` | `#FFFFFF` | Карточки и панели |
| `--color-surface-muted` | `#F8FAFC` | Вторичные области |
| `--color-text` | `#172033` | Основной текст |
| `--color-text-muted` | `#526176` | Вторичный текст |
| `--color-border` | `#DCE3EC` | Границы и разделители |
| `--color-primary` | `#2563EB` | Основные действия и активная навигация |
| `--color-success` | `#16845B` | Успешно / в норме |
| `--color-warning` | `#A96508` | Предупреждение / скоро срок |
| `--color-danger` | `#C63838` | Просрочка / критическая проблема |
| `--color-info` | `#2563A6` | Информация |

Отдельно определить токены ролей и токены состояний SLA. Не использовать один и тот же цвет одновременно для роли, этапа процесса и SLA. Цвет не должен быть единственным носителем смысла: всегда дополнять его текстом/иконкой/формой.

### 5.3. Типографика и размеры

- Основной текст: 14–16 px.
- Подписи интерфейса: преимущественно от 12 px.
- 10–11 px разрешать только для вспомогательной шкалы/декоративных меток, не для критичной информации.
- Заголовок страницы: 26–32 px на desktop, адаптивно меньше на мобильном.
- Заголовок карточки/секции: 18–22 px.
- Числовые KPI: 28–36 px, с табличными цифрами.
- Высота основных интерактивных элементов: ориентир 40–44 px; минимальные размеры проверять на соответствие WCAG 2.2 AA и реальному сценарию.

### 5.4. Сетка и адаптивность

Целевые контрольные ширины: 390, 768, 1024, 1440 и 1920 px.

- Desktop: фиксированная боковая навигация ориентировочно 240–260 px; основная область резиновая.
- Tablet: боковую навигацию можно сворачивать в компактный режим.
- Mobile: компактная верхняя панель и мобильное меню/нижняя навигация; KPI в одну или две колонки; таблицу преобразовывать в карточки либо использовать осмысленное горизонтальное прокручивание с видимой подсказкой и доступом с клавиатуры.
- Не допускать горизонтального переполнения всей страницы.
- У графа и Ганта допустим внутренний горизонтальный скролл: обязательны `tabindex="0"`, понятное accessible name, визуальный индикатор прокрутки и сохранение заголовков/ориентиров.

## 6. Состав экранов и требования к ним

### 6.1. App Shell

Единая оболочка:

- Sidebar: знак/название продукта, пункты навигации, активный раздел.
- Topbar: заголовок/контекст страницы, поиск (если он реально работает), дата/срез демо, информация о демонстрационном режиме.
- Main content: единая ширина, сетка и отступы.
- Общие состояния: загрузка (если применимо), пустой результат, ошибка, недоступная возможность.

Не выводить аватар/профиль/уведомления как интерактивные фальшивые элементы. Если функция отсутствует, элемент не показывать либо обозначить как макет/недоступный.

### 6.2. Обзор (`#dashboard`)

Структура:

1. Заголовок «Обзор» и пояснение, что отображаются демонстрационные данные.
2. KPI-карточки:
   - всего заявок в выбранном срезе;
   - требуют внимания (правило должно быть явно определено);
   - с приостановленным SLA;
   - просроченные.
3. Блок «Требуют внимания» — несколько наиболее приоритетных заявок с номером, кратким названием/ситуацией, SLA и текущим узлом.
4. Блок активности/последних событий — только если события можно корректно получить из модели.
5. Быстрые переходы к обращениям и хронологии.

Правила:

- Все KPI рассчитывать из существующего состояния/селекторов `src/core/`, а не вбивать числа вручную.
- Формулу «требуют внимания» документировать и покрыть тестом.
- Синхронизировать выбранную дату с URL, если обзор отображает временной срез.
- Нулевые состояния должны быть осмысленными, не ошибочными.
- Не показывать проценты SLA-эффективности, среднее время решения или тренды, если для них нет корректных данных.

### 6.3. Список обращений (`#incidents`)

Табличное представление на desktop с полями, которые реально доступны в модели:

- номер заявки;
- краткое название/ситуация;
- приоритет;
- текущий узел/этап;
- роль или ответственный, если это можно однозначно определить;
- состояние SLA и время/дедлайн, если доступно;
- дата последнего события;
- переход к карточке.

Функции:

- поиск по номеру и доступным текстовым полям;
- фильтр по приоритету;
- фильтр по SLA (в срок / пауза / просрочено / нет норматива — согласно существующей модели);
- фильтр по текущему узлу/роли, если поле доступно;
- сортировка по номеру, приоритету, дате и срочности;
- сброс всех фильтров;
- сохранение параметров в URL, если это согласуется с текущим роутером.

Не добавлять фиктивные поля «ФИО заявителя», адрес, телефон, исполнитель или сумма, если они не присутствуют в модели. При недостатке данных явно обозначить границы демонстрационной модели.

### 6.4. Карточка обращения (`#incident/<id>`)

Верхняя область:

- номер и название/ситуация;
- приоритет;
- текущий статус/узел;
- демонстрационная дата среза.

Основная область:

- текущий этап и краткое пояснение;
- SLA: состояние, норматив, дедлайн/остаток/просрочка — использовать существующие функции SLA;
- история переходов по узлам с датой и ролью;
- блок «Следующий шаг» только когда следующий шаг можно безопасно определить из графа с учётом прав и ветвлений. Если есть несколько допустимых ветвей, показывать варианты как варианты модели, не утверждать один из них как обязательный.
- ссылки на хронологию и чат с сохранением ID и даты.

Карточка должна работать как read-only представление текущей модели. Кнопки «Назначить», «Закрыть», «Отправить» не добавлять, если соответствующие операции не реализованы и не протестированы.

### 6.5. Хронология

Сохранить две визуализации одних и тех же данных:

- Git-граф — детальная карта ветвлений и событий;
- Гант — обзор распределения заявок и интервалов по времени.

Улучшения:

- более понятная шапка и управление датой;
- чёткое переключение Git/Гант;
- читаемая легенда SLA и развилок;
- масштабирование/управление плотностью, если реализуемо без изменения модели;
- ясный фильтр по заявке и всегда видимый сброс;
- закреплённые заголовки колонок/узлов там, где это возможно;
- внутренний скролл с подсказкой, фокусом и клавиатурой;
- карточка узла с корректным фокусом, Esc и возвратом фокуса;
- все изменения даты/вида отражаются в URL;
- мобильная версия остаётся функциональной, а не просто уменьшенной копией desktop.

Не менять смысл линий, точек, ветвлений, цветов SLA и дат.

### 6.6. Переписка

- Представить как историю сообщений/плеер, а не полноценный мессенджер.
- Сохранить переключение ролей и реплик, дату и связь с заявкой.
- Сделать ясными отправителя, роль, дату и системные события.
- Оставить заметную маркировку «Демонстрационная переписка · только просмотр».
- Не выводить активное поле отправки сообщения.
- На desktop использовать ширину рабочего пространства; мобильный вид оставить как адаптивный layout, а не обязательно как рамку физического телефона.

### 6.7. Модель процесса и ситуации

Сохранить доступ к 30 узлам, 7 ролям, уровням прав и 37 ситуациям. Улучшать читаемость, группировку, заголовки и адаптивность. Не менять нормативный текст и семантику без согласования. До реализации самостоятельного раздела «Ситуации» изучить текущий `#model` и решить, можно ли представить данные без дублирования.

## 8. Этапы реализации

Этапы выполнять строго последовательно. Каждый этап завершается тестами и коротким отчётом до начала следующего.

### Этап 0. Инвентаризация и фиксация baseline

**Оценка:** 0,5–1 рабочий день.

Задачи:

1. Прочитать `AGENTS.md`, `README.md`, текущий план и аудит UI.
2. Проверить дерево файлов и фактическую архитектуру `src/web/`.
3. Запустить существующие unit, typecheck, build, e2e и аудит — записать результаты.
4. Снять исходные скриншоты 390/768/1024/1440 px для всех текущих экранов.
5. Описать текущие маршруты, UI API, селекторы данных, существующие CSS/тему.
6. Составить точную матрицу «экран → компонент → источник данных → тест».
7. Не менять продуктовый код, кроме исправления блокирующей инфраструктурной проблемы после отдельного объяснения.

Критерии приёмки:

- есть `docs/redesign-baseline.md`;
- команды и результаты тестов зафиксированы;
- перечислены реальные файлы и точки входа;
- определено, какие данные можно вывести без новой бизнес-логики;
- нет изменений модели и поведения.

### Этап 1. Design system и App Shell

**Оценка:** 1–1,5 рабочих дня.

Задачи:

1. Ввести токены цвета, типографики, отступов, радиусов, границ, теней и breakpoint.
2. Реализовать общую оболочку: Sidebar, Topbar, PageHeader и контейнер содержимого.
3. Определить адаптивное состояние боковой навигации.
4. Создать базовые компоненты статусов, приоритетов, KPI и пустого состояния.
5. Подключить токены к текущим экранам без регрессий.
6. Сохранить доступность и существующий механизм темы.

Критерии приёмки:

- общая оболочка отображается на существующих экранах;
- светлая тема визуально целостная;

### Этап 2. Обзор и список обращений

**Оценка:** 1,5–2,5 рабочих дня.

Задачи:

1. Добавить маршрут `#dashboard` и экран обзора.
2. Вычислять KPI из существующей модели и даты среза.
3. Определить и документировать формулу «требуют внимания».
4. Добавить список обращений `#incidents`.
5. Реализовать поиск, фильтры, сортировку и сброс.
6. Сохранить фильтры в URL, если это согласовано с роутером.
7. Сделать пустые состояния и явную маркировку демо-данных.
8. Связать KPI с отфильтрованным списком.

Критерии приёмки:

- Dashboard не содержит вручную заданных KPI;

- поиск и фильтры работают на клавиатуре и мышью;

### Этап 3. Карточка обращения

**Оценка:** 2–3 рабочих дня.

Задачи:

1. Добавить детальный экран выбранной заявки.
2. Отобразить приоритет, текущий узел, дату среза и состояние SLA.
3. Построить понятную историю движения по узлам и ролям.
4. Корректно обработать разветвления и несколько возможных следующих шагов.
5. Добавить переходы в Git-граф/Гант и переписку с сохранением ID и даты.
6. Обработать неизвестный ID и отсутствие истории.
7. Сделать карточку доступной с клавиатуры и корректной для скринридеров.

Критерии приёмки:

- карточка показывает те же данные, что соответствующая заявка в хронологии;
- SLA рассчитывается существующей логикой;
- не выдумываются персональные данные и операции;
- история сохраняет фактический порядок и даты событий;
- все переходы сохраняют контекст;
- неизвестный ID не вызывает падение приложения;
- e2e проверяет открытие из списка, прямую ссылку, переходы в хронологию и чат.

### Этап 4. Редизайн хронологии, Ганта, переписки и модели процесса

**Оценка:** 1,5–2,5 рабочих дня.

5. Сделать внутреннюю прокрутку графа/Ганта доступной с клавиатуры.
6. Закрепить заголовки узлов там, где это технически возможно.
7. Улучшить мобильный режим: подсказки скролла, перенос/компактный выбор заявок, адаптивная карточка.

Критерии приёмки:

## 9. Команды проверки

Использовать команды, объявленные в актуальном `package.json`. На момент подготовки плана они включают:

```bash
bun test
bun run typecheck
bun run build:demo
bun run e2e
bun run audit
```

Для ручной проверки:

```bash
bun run serve:demo
```

Не считать задачу завершённой, если тесты не запускались. Если команда не может быть запущена из-за отсутствующего браузера, окружения или сети, зафиксировать точную причину и выполнить максимально возможную локальную проверку.

## 11. Порядок работы с Claude Code

Для реализации использовать отдельный файл `docs/claude-code-redesign-tasks.md`.

1. В начале новой сессии Claude Code читает `AGENTS.md`, этот план и актуальный audit.
2. Запускается только задание текущего этапа.
3. Не переходить к следующему этапу, пока текущий не прошёл приёмку.
4. Не выполнять массовые переписывания/форматирования несвязанных файлов.
5. Не делать `git push`, не менять настройки GitHub Pages и не удалять исходные страницы без отдельного разрешения.
6. После каждого этапа выдать краткий отчёт и остановиться.

## 12. Риски и решения

| Риск | Мера |
|---|---|
| Новые экраны требуют полей, которых нет в модели | Перед реализацией составить data map; отсутствующие поля не выдумывать |
| Редизайн ломает deep links | Сохранить hash API и добавить e2e на старые URL |
| CSS новой оболочки конфликтует с графом/чата | Область действия классов ограничивать компонентами; регрессионные скриншоты |
| Визуальные статусы расходятся с SLA | Использовать только существующие функции `src/core/` |
| Фальшивые действия создают ложное впечатление продукта | Не показывать неподдерживаемые операции или маркировать их как недоступные |
| Мобильный граф остаётся слишком широким | Сохранить внутренний scroll с подсказками, фокусом и ориентиром узлов |
| Слишком большой scope | Первым релизом ограничиться обзором, обращениями, карточкой и редизайном текущих экранов |
